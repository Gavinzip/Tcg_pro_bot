## 為何從二十幾秒變慢

相同 4 RPS 下，備份與掃描雖是不同程序，仍共用同一容器、2 GB 記憶體與 `/data` 磁碟。現行備份會做 SQLite 線上複製、完整性檢查、雜湊及 restic 加密上傳；現行 supervisor 沒有讓掃描優先，兩種重工作會同時執行。

相同 127 個成功回覆的離線舊／新版對照：每 receipt 10 logs 時 1.979 → 2.216 ms，每 receipt 100 logs 時 6.884 → 7.290 ms，結果相同、外部查鏈呼叫零。這只量回覆處理成本，不能當正式整輪效能保證。`store.py`／`query_retention.py` 在 PR10 沒有變更。

4 小時平台統計的記憶體峰值接近 2 GB 限額，CPU 峰值約 0.92／上限 2；不是 OOM 或磁碟滿的證明。正式時序、相同請求數比較與本機 supervisor 的並行重現，共同定位到未協調的備份資源競爭。沒有 production I/O syscall trace，無法把歷史每一秒再分成磁碟等待、cache reclaim 或 SQLite 鎖；不把相位定位冒充這些細項已量到。

## 已獲准的本機修正

- 加入跨程序的掃描優先 gate。掃描先取得 intent，備份完成當前有界 I/O 段後讓出 work；鎖由 kernel 管理，程序退出不會留下 PID 標記永久阻塞。
- SQLite 在 `backup_step` 回來、來源讀鎖已釋放的 page 邊界讓出；雜湊與一般檔案複製按 1 MiB 分段，完整性檢查在 staging DB 的 VM 邊界讓出。沿用 [SQLite online backup](https://www.sqlite.org/backup.html) 與 [WAL](https://www.sqlite.org/wal.html)，不直接複製活動中的 WAL 主檔來假裝一致備份。
- WAL 備份固定同一 read view，避免每次掃描新增紀錄都讓暫停中的複製重頭開始。正常掃描仍可寫 WAL；測試確認來源新增紀錄保留，而備份保持一致的原視圖。
- restic／rclone 上傳讀的是 staging／穩定媒體，可以暫停整個 process group；確認停止後才讓掃描進入，掃完再繼續。掃描已在執行時不先啟動 uploader。沒有直接把可能持有來源 DB 鎖的 Python capture 程序硬停在任意指令。
- 保留原本逾時上限，掃描等待 priority admission 也受限。取消／逾時會釋放鎖、終止分開的 uploader group、清理本次 invocation 的 staging；不清理別人的舊檔、不刪正式資料。
- 每日備份、完整還原驗證、掃描頻率、4 RPS、付款與計票規則保留。本次無新增 fallback 或查鏈請求。

原版真實 supervisor＋backup subprocess 測試失敗：掃描期間 uploader 計數從 3 增至 22。修正後 uploader 與模擬 rclone 子程序都停止推進，掃描結束後備份繼續且成功。其餘驗證包括掃描先啟動、取消、admission／upload 逾時、真實 WAL concurrent write＋一致複製，以及真實本機 restic 加密備份／隔離還原。macOS 本機通過不代替 Linux CI 或正式驗證；不能先宣稱雲端已消除備份時段延遲。

## 每輪 API 怎麼算

以目前單一 builder／V3 來源、正常增量、無分頁拆區塊、無重試的實際樣本：

**總次數 = 固定定位／查 logs 成本 + N 個新交易 receipt + U 個尚未快取的交易區塊讀取。**

N 是需要新驗證的唯一交易雜湊數，包含回掃補到的交易；U 是它們所在的不同、尚未在本輪讀過的區塊數。不是每張卡、每個 token 或每抽都打一個 receipt。已驗證的舊回掃紀錄重用證據；同交易多個 checkout 重用 receipt，同區塊重用區塊讀取。

下列正式樣本的固定成本都是 **9**：head 1、確認界線區塊 1、checkpoint anchor 1、時間提示 1、精確時間邊界區塊 3、回掃 logs 1、前進 logs 1。

| 樣本 | N receipts | U 額外區塊 | 固定成本 | 合計 |
| --- | ---: | ---: | ---: | ---: |
| 11/25 18:25:55 | 23 | 20 | 9 | 52 |
| 11/26 11:42:13，發布前 | 38 | 34 | 9 | 81 |
| 11/26 11:44:32，發布後 | 61 | 57 | 9 | 127 |
| 11/26 11:51:11，備份中 | 39 | 33 | 9 | 81 |
| 11/26 12:00:49，備份後 | 39 | 33 | 9 | 81 |

例：10 筆交易分散在 10 個尚未讀過的區塊，該樣本路徑約 `9+10+10=29` 次；100 筆交易落在 20 個未快取區塊，約 `9+100+20=129` 次。固定定位成本會因邊界搜尋、首次建游標、多來源、分頁／拆區塊改變，不保證永遠為 9。

失敗後真正重試會多一次請求；PR10 已核准的無效時間提示備援也可能多讀區塊。安全格式檢查／紀錄及這次備份協調本身都是 **零額外查鏈 API**。輪次被備份拖長，下一輪涵蓋時間變長、累積更多交易，也會讓單輪 N／U 變大，不能誤算成新增驗證。

安全證據保存在 `.scratch/db-contention-evidence/`，不含真實 key、token 或完整錢包。本機驗證未刻意觸發正式備份、未停止正式掃描，也未增加付費 BSC／Solana 查詢。
