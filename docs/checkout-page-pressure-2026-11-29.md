# 付款分頁容量退化：本機修正

本報告記錄本機修正與測試；使用者已於 2026/11/29 授權 push、PR 檢查後合併及自動部署，正式驗收另保存於本機發布紀錄，不將本機測速當成正式結果。沿用 `codex/api-scan-cadence`，基底 `be5f4b742090b5737f0165b9552808606f6ea74c`（已合併 PR #14）。網站基底 `ae97f43ef310dffcb6433c5620d45f46e9b6dcb6`；這次沒有修改網站產品程式，也沒有混入尚未發布的前端版本銜接修正。

## 資料流程與問題

鏈上付款 → 原始帳本 SQLite → **可分頁的付款明細投影** → 活動後端完整驗證／計票 → **已完成的排行榜** → 網站／Partner。

兩個粗體部分用途不同：前者是後端整理榜單的原料，後者才是訪客看到的結果。原始紀錄先持久保存於帳本，並不只存在快取。

PR #14 讓相同 event／revision／snapshot／builder 共用整理結果，但最多保留兩份、合計 128 MiB 的 JSON 序列化大小。超大的投影不會被留下；兩份各自放得下、合計超額的投影交錯讀取時，也會互相淘汰。下一頁因此重新解碼、整理整份歷史。128 MiB 不是 Python heap 上限，物件展開可占更多記憶體。另外，每頁原本即使命中快取，仍先解碼所有玩家身分。

新增回歸先在舊程式復現：單份 3,000 筆／三頁重讀 9,000 筆；兩份快照交錯也重複整理。同樣工作在修改後各快照僅整理一次。

已保存的正式事故紀錄：台灣 11/29 01:39–01:42 左右來源 `/checkouts` 共 69 次 200，中位數 6,560 ms、最長 8,672 ms，分屬兩組用戶端。掃描輪次仍成功、約 8–16 秒；網站記錄 `checkout_sync_time_budget`（整次收齊付款證據的 300 秒預算，非單頁期限）。先前窗口分頁最快、最慢模式差距顯著。

**歷史事故的歸因限制：**當時沒有 query pin／cache bytes／hit／eviction 記錄，因此不能斷言那 69 次必定是哪一種容量退化。這次證明並修復可重現的程式缺陷；正式改善仍需部署後核對新診斷，沒有把上游網路／SQL 所有延遲都宣稱已排除。

## 修改

- 同一固定快照的付款明細，逐筆整理到可重建的本機 SQLite 投影。完整建好才加入可讀清單；每頁依整數主鍵範圍讀取，最多解碼 1,000 筆。
- 相同快照的並發請求共用一次建置；投影以 event／revision／snapshot／builder 隔離，使用 LRU。
- 每頁仍讀最新來源健康、設定版本、保留期限與 builder 範圍；只有快取未命中時才展開全部玩家身分。
- 預設最多 16 份磁碟投影、總計 2 GiB；每個 SQLite 頁快取約 1 MiB，寫入批次最多約 1 MiB 或 1,000 筆。單筆資料及玩家身分本身仍有成本，不把這些數字稱作整個程序的硬記憶體上限。
- 磁碟額度／I/O 失敗回明確 503 `checkout_cache_unavailable`；不回部分明細、不借其他快照。清除損壞投影後，下次可用同一固定快照重建。未新增資料 fallback 或放寬驗證。
- 建置及超過一秒的分頁記錄安全診斷：作用範圍雜湊、頁數、耗時、磁碟用量、整理筆數。沒有地址、交易內容或憑證。

原本的成功回應欄位、網址、授權、cursor、排序及快照語意保留。原始帳本、掃描／計票規則、RPS、金鑰、64 confirmations、五分鐘回掃皆未修改；沒有延長 300 秒同步期限。

## 同一工作量 A/B

合成 100,000 筆有效付款／11,150 位玩家，同一 SQLite fixture、兩份固定快照，走正常來源 HTTP server／授權／controller。舊版 store／cache 從基底 Git 原碼載入記憶體，新舊分別在新程序執行，沒有切換 checkout。

| 項目 | 部署基底舊版 | 本機新版 |
|---|---:|---:|
| 相同 12 次交錯分頁總時間 | 10,847 ms | 2,259 ms |
| 相同 12 次請求整理的原始筆數 | 1,200,000 | 200,000 |
| 相同 12 次請求完整身分讀取 | 14 | 4 |
| 程序峰值 RSS | 720.86 MiB | 158.62 MiB |

相同 12 頁內容 SHA-256、抽數與付款金額完全一致。新版另續取完兩份各 100,000 筆：200 次 HTTP、4,450 ms、中位數單頁 8.13 ms，冷建置最長頁 1,150 ms；共整理 200,000 筆、198 次命中、零淘汰，投影磁碟 164,257,792 bytes。

RSS 是各自整個程序觀察的峰值；新版涵蓋全部 200 頁，舊版僅跑相同的 12 頁。沒有測量舊版完整 200 頁耗時，不能把推估當實測。以上是本機 loopback／SSD，不能當成 Railway/WAN 發布後速度；OS 檔案快取也不包含在程序 RSS 裡。

## 完整計票驗證

`scripts/verify_checkout_ranking.mjs` 使用網站當前正常 `createLeaderboard`／完整付款 SQLite 同步／`createCampaignRanking`／獎勵帳本，透過本機正常來源 HTTP 讀取同一合成資料，使用獨立測試目錄與測試授權：

- 100,000 筆、11,150 位玩家 → 100,000 抽／500,000 票（隔離 fixture 每抽五票）。首次完整整理約 2,859 ms。
- 相同來源重讀重算，票數與所有排名列 digest 相同。
- 同一已驗證任務證據重複入帳，只有一筆 grant／兩張額外票，總票 500,002；個人該列只增加兩票。
- 固定舊 snapshot 的列與統計不變。來源只建一份投影、處理 100,000 筆，99 次快取命中。
- 這是後端讀取／計票整合驗證，沒有模擬成正式玩家操作驗收；零正式／付費 BSC、Solana 呼叫。

完整回歸 **267 項全通過、零略過**，包含掃描、付款證據、builder、版本、保留期限、快照、並發、排程、備份優先權及 HTTP 授權。新增儲存失敗、部分寫入後證據衝突、損壞快取與交錯版本案例。精確測試結果保存於 `.scratch/payment-sync-20261129/regression.log`；本次未另重跑需要 restic 的加密備份還原套件，沒有修改該實作。

這輪是 100,000 筆驗證，**不是一億筆容量驗收**。2 GiB 磁碟上限仍有限，超額會明確報錯，不承諾任意資料量／並發版本都不重建。首次新快照仍需整理一次全量，該成本及玩家身分量隨資料成長，後續增量／大容量工作仍須另測；本輪沒有暗中改變對外接口或採信不完整付款。
