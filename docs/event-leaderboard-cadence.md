## 已確認與尚未確認

歷史兩個慢輪次約為台灣時間 08:20–08:25、08:25–08:36，服務在窗口內持續查詢 Etherscan。但舊版沒有保存每輪 action／階段統計，主程序也丟棄子程序輸出，因此尚不能證明當時多查的是區塊、receipt，或其他查詢。下方測試是合成案例，不是歷史兩輪的原始請求重播。

已在實際 provider 程式路徑復現一項缺陷：時間轉區塊的提示偏差 300 個區塊時，舊版逐塊校正需要 303 次請求。第一版用倍增範圍及二分搜尋降至 20 次。續查發現本輪已讀取的 canonical 區塊可作為現成定位錨點，因此再以這些區塊縮小範圍，最多兩次依時間比例推算位置，並查核前一區塊來證明精確邊界。

保底行為：若時間間隔不規則或同秒區塊很多，兩次推算後仍以二分搜尋收斂。原因是避免插值在不規則分布下退化成大量查詢；影響是可能增加幾次區塊讀取，但不替換來源、不省略付款與 canonical block 查核。錨點只取本輪 provider 的已讀區塊，head() 開始下一次同步時會清空，不跨輪沿用舊鏈狀態。

## 診斷內容

正常入口仍是 `scripts/sync_event_leaderboards.py`，診斷行以 `[event-scan-diagnostic]` 開頭，寫到 stderr；主程序即時驗證格式後轉寫服務日誌。每輪有共用 run_id，活動使用 event_id 的 SHA256 前 16 位 event_ref，不記錄錢包或金鑰。

- 記錄實際開始／完成與耗時，區分 startup、head、boundary、checkpoint、overlap、forward_logs、receipt、驗證、commit、publish。
- 每階段與每種 action 的實際嘗試次數；逾時、成功前重試、HTTP 錯誤分類、限速等待、重試等待與供應商回應耗時。
- 邊界提示與定位結果、掃描區塊範圍、補掃驗證筆數與補入筆數；可對照 receipt 階段次數判斷是否為新增交易查核。
- 長輪次在請求進行中約每 30 秒輸出累計統計；timeout 或中止保留已輸出的階段記錄。單次長 I/O 期間由 phase_started 標示所在階段。
- 每筆交易的 phase 只累計，不逐筆輸出，避免大量日誌反過來拖慢掃描。階段 elapsed_ms 包含子階段，不能相加當作整輪耗時；請使用 finished.elapsed_ms。請求次數採目前所在階段歸屬，可相加。
- 只接受封閉欄位及數字統計，不輸出完整 URL、key、provider body、raw stderr 或例外內容。

這些秒數是模型值，未計入真實 SQLite、CPU、網路波動與啟動成本，不能當作正式 SLA。交易增加或供應商逾時仍可能超過一分鐘。沒有提高請求速率，也沒有改動 64 confirmations、補掃窗口、去重或票券規則。
