本文件記錄本機根因修正與驗證結果；正式發布須另核對 PR 合併、production deployment 及功能。下列測速均不是正式環境發布後的測量。

- 掃描器 checkout：`/Users/gavin/.codex/worktrees/scanner-boundary-root-cause/tcg_pro_bot`，分支 `codex/scanner-boundary-root-cause`，基底 `00dfcf339b972330085dc751785119f954da79a9`。
- 活動後端驗證 checkout：`/Users/gavin/.codex/worktrees/bnb-api-scan-cadence/b-w`，分支 `codex/api-scan-cadence`，上傳前同步基底 `620cfb8882c827c156d00487a192bbc62bc06503`（新增的六個前端檔案不涉及本次後端修正）。既有交接文件及 Partner 測試保留；沒有混入本輪掃描器修改。

## 發生原因

掃描成功與網站完成換榜是不同階段。活動 API 遇到新來源快照後，會固定 snapshot ID，逐頁收齊付款證據，再做全域計票與發布。

來源 `/checkouts` 原本先呼叫 `read_checkout_snapshot()`：讀取整份凍結付款歷史、逐筆解析 JSON、檢查區塊／時間／builder、套用凍結身分，再由 HTTP 層取出要求的 1,000 筆。下一頁又完整重做。10 萬筆、100 頁等於遍歷約 1,000 萬筆，而不是只遍歷一次。來源在每分鐘完成新快照，無法讓正在下載舊版完整證據的活動 API 立刻跳到新版本；跳頁混版反而會破壞完整性。

正式既有日誌（UTC 2026-11-27 16:00–16:16，台灣 11/28 00:00–00:16）提供相符證據：

- 684 個活動來源讀取，其中 678 次 `/checkouts`；付款頁中位數 2,257 ms、P95 3,070 ms、最慢 5,078 ms，677 次 200、1 次 499。
- 來源水位查詢僅 6 次、約 50–300 ms。掃描仍持續成功，每輪約 7–12 秒。
- 日誌出現兩組 Node 來源位址；沒有 query string，不能精確把每頁歸入哪個快照或哪個客戶端，不能把全部請求都歸給單一正式程序。
- 00:09:24 網站資料截止 00:00:16，故為落後 548 秒；不是掃描花了 548 秒。00:14 複查已換成截止 00:09:16 的新榜。

上述正式日誌加上原版完整鏈路的可重現延遲，確認了重複全量整理這個瓶頸。歷史 548 秒缺少逐階段 span，不能捏造每一步的精確秒數，也不能宣稱已排除所有正式環境因素。

## 本機修改

- 新增 `checkout_pages.py`，只重用同一 event／revision／snapshot／builder 的不可變付款投影，HTTP 只複製要求的頁面。新快照獨立整理，並發讀取同版共用一次整理。
- 每次請求仍先從資料庫檢查最新健康、活動 revision、builder、快照存在及保留期限；不快取健康狀態。來源明確失敗仍回報 stale／last_error，由原有消費端拒絕拿來發獎。
- 最多保留 2 個投影，合計最多 128 MiB 的序列化資料；這不是 Python heap 上限。超出容量時執行原本完整資料讀取，不回傳另一版或另一來源；此為正常 cache miss，不新增舊榜／資料來源 fallback。
- 回傳頁面深複製，客戶端修改巢狀 aliases 不能污染其他頁。到期舊版即使還在 RAM，也先拒絕。
- 固定截止時間只解析一次，避免逐筆重複轉換。
- 活動 API 在核實新版水位後，先釋放被新版取代的完整原始付款證據，再收集新頁；並行的付款證據查詢共用新載入。已準備完成的可見榜單獨立保留，沒有變動舊榜的時間／snapshot，也不讓過時的 raw proof 沿用原 30 秒 TTL。對應 `server/leaderboard.mjs` 及 `server/tests/ranking-cache.test.mjs` 在網站 checkout 本機修改，本機驗證後作為獨立網站 PR 上傳。
- 沒有改掃描演算法、付款證據、64 confirmations、五分鐘回掃、開始間隔、RPS、金鑰、日期或計票規則。鏈上請求路徑未改。

## 能抓到本次問題的測試

`tests.test_event_checkout_paging_cost` 先在原版失敗：5,000 筆分成 5 頁卻整理 25,000 筆；修後只整理 5,000 筆。另涵蓋並發、快照重啟、補入舊區塊、凍結別名、builder、revision、來源錯誤、快照到期、回覆可變物件隔離、容量淘汰、超容量及失敗載入。

原版／修正版的獨立完整鏈路使用相同合成 10 萬筆，透過本機 SQLite＋真正掃描器 HTTP controller＋活動來源讀取與計票服務。原版程式由 Git 基底載入記憶體，沒有切回或覆蓋工作檔案；兩版順序執行：

| 指標 | 原版 | 修正版 |
| --- | ---: | ---: |
| 啟動收齊並產生榜單 | 73.73 秒 | 6.74 秒 |
| 下一份完整快照換榜 | 78.66 秒 | 7.17 秒 |
| 兩次完整讀取的內部來源 HTTP 次數 | 201 | 201 |
| 新增鏈上 API 呼叫 | 0 | 0 |
| 總抽數／總票數 | 100,000／800,000 | 100,000／800,000 |

兩版排序與票數的完整 row digest 相同，舊 pinned snapshot 不變；原版換榜超過 60 秒測試明確紅燈，修正版通過。來源單獨修正的第一次完整對照為 7.72 秒；上表修正版採後續加上 raw proof 釋放後的最終重跑。同時驗證 25,000→25,001 筆新交易：+1 抽、+8 票，新來源 cutoff 完整對上，約 1.87 秒完成服務換榜。

201 次是同樣兩次完整更新的內部 HTTP 次數；修後能更頻繁追上新快照，一天內的自家服務讀取總量可能隨完成頻率增加，不能把單輪相同說成每日內部 HTTP 次數必定相同。這些讀取來自 SQLite，不是 BSC／Solana 付費鏈查詢；掃描器的鏈上查詢頻率及路徑未改。

另啟動真正 `createApp` 的 HTTP server，測網站與帶隔離測試密碼的 Partner API：新快照一致、搜尋、排序、固定版本分頁無重複、舊版不改寫、`Cache-Control: no-store`。25,001 筆新交易驗證約 1.50 秒換榜；100,000 筆換榜約 7.23 秒。這些是隔離的本機契約／效能測試，不是正式 Partner 密碼複驗，也不是產品前端預覽。

初步 controller-only 不同量測曾有程序重疊，原始資料仍保留；上表採後來順序執行的完整鏈路，不把不同測量層級混為一談。

## 回歸、限制與證據

- 掃描器工作流程相同模組的 260 項測試通過；新的 5 項針對性測試通過。
- 活動後端完整測試：184 通過、6 項既有選配測試略過（含隔離磁碟路徑／大型啟動及 restic 需求），不是 190 全過。這輪另有真實 SQLite＋HTTP 10 萬筆測試。
- 追加限制 heap 的獨立 API 程序驗證：10 萬筆在 256 MiB old-space 限制下，原本雙份 raw proof 的換榜發生 heap OOM；釋放被新版取代的 raw proof 後，相同限制完成換榜約 7.15 秒，API peak RSS 約 420.7 MiB。這是本機壓力情境，不是正式 OOM 根因證據。來源程序在該測試 peak RSS 約 863.4 MiB（含診斷端發布新版本的額外完整讀取）；不是宣稱快取只耗 128 MiB heap。原本同程序客戶端／API 測量的 562 MiB 不拿來當伺服器用量。
- 首次自訂 Python runner 的模組 regex 截斷 `v3` 名稱，曾有 import error；修正 runner 後全量 260 通過。網站首次因這個舊 checkout 缺少最新 lockfile 的 `@vercel/functions` 而失敗；同步既有依賴後完整後端測試通過。失敗紀錄未抹除。
- 沒有呼叫正式付費 BSC／Solana API；只讀取自家平台既有日誌。未取得正式來源 token，因此沒有新增正式全量下載或刻意製造來源失效。
- 保留原本每頁 1,000／最多 100 頁（10 萬付款紀錄）的同步安全上限。100,001 筆會明確拒絕，沒有靜默漏頁或放寬上限。網站「抽數」不等於付款紀錄筆數；擴大上限需另外確認，不屬這次修正。
- 快取可能因重啟、容量而重新整理一次；付款／加分／排名語義不依賴 RAM。正式 WAN、CPU 配額及多服務競爭仍須在授權部署後驗證，不能以本機 7.7 秒保證每輪正式換榜 SLA。
